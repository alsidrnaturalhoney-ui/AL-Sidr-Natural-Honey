# AL SIDR JARVIS Core v1 — Foundation & Security Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the trusted JARVIS Core v1 runtime foundation: typed execution contracts, deterministic routing, capability registry, non-bypassable policy decisions, execution/verification/audit engines, secure Supabase persistence, and CI gates.

**Architecture:** Extend the existing `@alsidr/jarvis-core` TypeScript package rather than creating a parallel runtime. All actions flow through typed request → route → plan → policy → execute → independently verify → audit; Supabase is server-only runtime persistence for this phase, with direct client access denied by RLS/policies and no external production write capability enabled.

**Tech Stack:** Node.js 22; TypeScript 5.8.x; Zod 3.25.x; Vitest 3.2.x; npm workspaces; Supabase/PostgreSQL 17; GitHub Actions.

**Spec:** `docs/superpowers/specs/2026-09-13-jarvis-core-v1-design.md`

## Global Constraints

- Extend the existing `JARVIS-OS`, `ai-os`, and `packages/jarvis-core`; do not create a parallel operating system.
- Live verified system data overrides stale documentation, assumptions, or model memory.
- Read before write and prefer the least-privileged, least-destructive capability.
- Every external/tool action must pass the policy gateway; the model cannot downgrade or override its result.
- Risk vocabulary for Core v1 is exactly `R0`, `R1`, `R2`, `R3`.
- Policy decisions for Core v1 are exactly `ALLOW`, `ALLOW_NOTIFY`, `REQUIRE_CONFIRMATION`, `DENY`.
- Material writes require independent verification before success is reported.
- No `service_role`, private keys, tokens, secrets, customer PII, or credentials may appear in browser code, Git, prompts, logs, or docs.
- Supabase runtime tables are server-only in this phase; direct `anon` and `authenticated` table access remains denied.
- Do not enable Shopify/customer/public-publishing/financial/destructive production writes in this plan.
- English/Arabic/RTL UI work belongs to the Console & AI plan, not this foundation plan.
- Use TDD for every behavior change: failing test → minimal implementation → passing test → commit.

- [ ] **Step 3: Implement deterministic policy precedence**

`evaluatePolicy()` must apply this exact order:

```ts
1. parse request, step, capability
2. deny if request capability != capability.name
3. deny if step capability != capability.name
4. deny if operation is not allowed
5. deny if any required permission is absent
6. deny if capability requires evidence and step evidence is empty
7. deny if actor is unauthenticated and capability risk != R0
8. deny if actor authStrength < capability.minimumAuthStrength
9. deny if capability requires rollback and step.rollbackReference is null
10. if confirmation == "always" and approvalReference is null -> REQUIRE_CONFIRMATION
11. if confirmation == "risk-default":
    R2/R3 without approval -> REQUIRE_CONFIRMATION
12. R0 -> ALLOW
13. R1 -> ALLOW_NOTIFY
14. approved R2/R3 -> ALLOW
15. catch/parse failure -> DENY
```

Return stable, audit-friendly reasons such as `missing_permission`, `operation_not_allowed`, `approval_required`, `strong_auth_required`, and `policy_prerequisites_satisfied`.

```ts
export function routeExecution(
  request: ExecutionRequest,
  capability: CapabilityManifest,
): "SYSTEM_1" | "SYSTEM_2" {
  const lowRisk = capability.risk === "R0" || capability.risk === "R1";
  const operationAllowed = capability.allowedOperations.includes(request.operation);
  return lowRisk && operationAllowed && request.confidence >= 0.95
    ? "SYSTEM_1"
    : "SYSTEM_2";
}
```

```ts
  | { status: "WAITING_APPROVAL"; policy: PolicyDecision }
  | { status: "CANCELLED"; policy: PolicyDecision }
  | { status: "FAILED"; policy: PolicyDecision; result?: ActionResult; verification?: VerificationResult }
  | { status: "VERIFIED"; policy: PolicyDecision; result: ActionResult; verification: VerificationResult };
```

- [ ] **Step 2: Write tests proving confirmation-required actions pause without invoking adapters**

- [ ] **Step 3: Write tests proving successful execution requires observation/verification**

The adapter returns `{ status: "EXECUTED", output: { id: "x" } }`; `observe()` returns `{ id: "x" }`; expected result is `{ id: "x" }`; final status must be `VERIFIED`.

- [ ] **Step 4: Write mismatch and cancellation tests**
